# GOSS启动保护失败、独立恢复守护实测及完整模型试运行

原12 GiB条件下的GOSS任务始终处于零拟合等待状态。依据已完成四个最大窗口分位树试验的3.24 GiB进程峰值，并额外预留4 GiB，建立独立的8 GiB入场试验。原六套GOSS参数、6,754,006行、63特征及300轮均保持一致；另一目标的内存观测不是GOSS内存上限。

第一次8 GiB尝试在FitHold保护检查中失败：WMI启动根进程脱离Job，并不代表虚拟环境重定向器的原生子进程也脱离其自身Job。失败发生在守护启动、调度暂停和原生模型拟合之前，模型权重0。下游等待器正确拒绝失败的父任务。失败源码、堆栈、资源及终态全部保留，不作为GOSS硬件边界证据。

修复采用真正独立的WMI守护服务。实际服务控制测试覆盖正常结束与有意os._exit(37)的异常退出；模拟调度器心跳确实暂停并恢复，异常情况下守护只恢复精确PID、创建时间及命令一致的模拟进程。两个控制均通过，实际科学训练及依赖进程触碰0。

原12 GiB零拟合等待任务已明确行政接管，未制造成功执行标记。失败8 GiB尝试已终态，修复后的完整范围工作流实际启动；第一套GOSS已进入最大窗口原生拟合。所有新启动和守护均无可见控制台，原GPU训练、第84轮及发布器继续运行。
